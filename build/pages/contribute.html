Contribute

Bring a GPU, a red pen or a keyboard

Lead Green is small and it is public. Its value is the number of independent, reproducible measurements on the index and the care with which each one is checked. Both grow faster with volunteers. Here is what is needed, how to do it, and the rules that keep a row defensible.

Roles

Five ways to help

Measurers

Run the protocol

You have access to a GPU server, on-premise or rented, and can run a serving engine under a fixed load for an hour. You produce rows.

Reviewers

Check the working

You can read a benchmark's method, recompute a figure from its raw file, and say whether a claim on the site survives contact with its source.

Writers

Explain one question

You can take one of the upcoming blog topics, or propose one, and write it with the working shown and every figure sourced.

Translators

Carry it across

The carbon table was chosen for readers in the Gulf, South Asia, South-East Asia and Central Europe. Translations of the index and the "why" page, checked by a second speaker, are welcome.

Developers

API and MCP

The build script, the JSON API and the MCP server are small Python. A hosted MCP endpoint, a per-model comparison tool, tighter OpenAPI schemas and a spreadsheet export are all open.

How

Issues and pull requests

Everything lives in {{REPO_LINK}}: the page sources, the build script, the dated data snapshots, the API and the MCP server. Propose a change as a pull request, or open an issue if you want to discuss it first. A measurement is submitted as a JSON file in the row schema below plus the logs it was computed from; a correction is submitted with a link to the primary source. There is no mailing list to join and no form to fill.

Contributors are credited by name on the change record and, for measurements, on the row itself. Bylines on blog posts are the author's own.

Measurement protocol v0.1

How to produce a row that can sit beside the public ones

  1. Serving engine. vLLM, the engine the public benchmark uses, so rows are comparable. Record the exact version. Other engines are welcome as clearly labelled separate rows.
  2. Hardware. Name the GPU model, memory, form factor (SXM, PCIe, NVL), count, and any MIG profile. Name the driver and CUDA versions and the host. If the card is shared with anything else, say so.
  3. Prompt set. A fixed, published prompt set with a stated average prompt length. The public benchmark uses an LM Arena conversation sample; a link or a file is required so another measurer can repeat it.
  4. Load. A fixed concurrency (max sequences), held long enough to reach steady state: at least five minutes after warm-up and at least 1,000 requests. Record the average running batch the server actually held (vLLM's num_requests_running, averaged over the window), not only the cap.
  5. Power. Sample GPU power at 1 Hz through NVIDIA DCGM (DCGM_FI_DEV_POWER_USAGE) or nvidia-smi --query-gpu=power.draw, for every card in the configuration. Integrate over the steady-state window for energy in joules.
  6. Tokens. Count output tokens served in the same window from the engine's own metrics, and record the average output length.
  7. Report. Joules per output token (energy ÷ output tokens), Wh per million (× 1,000,000 ÷ 3,600), median and p99 inter-token latency, tokens per second, average power summed across cards, and the fields above, in the JSON row schema used by the API. Attach the raw power log and the engine log.
  8. Repeat. Two runs; report both and the mean. If they differ by more than 5 percent, say why or run a third.

The protocol measures GPU energy only, like the index. If you also have facility or host power, report it as separate fields; do not fold it in. The same goes for water: if you know the site's water use, report it in the optional site water field as water usage effectiveness (litres per kWh of IT energy, ISO/IEC 30134-9), never folded into Wh/M. A sliced (MIG) card is measured on the slice's own metrics where the tooling allows, and the whole-card draw is reported alongside with the slice count.

Review rules

What it takes to land on the index

  • Two reviewers for a new row or a changed figure, one of whom recomputes the number from the attached logs or the source file.
  • Source snapshot. Every public figure is taken from a dated copy of the source file, kept with the site, so it can be recomputed later even if the source moves.
  • Claims ledger. Every figure on every page has a source and a retrieval date in the sources list. If it cannot be sourced, it does not ship.
  • Corrections are made in the open: the change record on the index names what changed, when and why, and a corrected blog post keeps a note at the top.
  • Vendor rows are labelled. A measurement made by or paid for by a hardware, cloud or model vendor is marked as such and shown separately from independent rows.
  • No customer names. A measurement from a production site is described by hardware and workload, not by whose site it is.

Needed first

The gaps, in order

  1. MIG slices. Any model on a 1g, 2g or 3g slice of an H100 or H200, against the whole card. Nothing public exists.
  2. Other GPUs. A100, H200, L40S, and AMD MI300X. The index has H100 and B200 only.
  3. Hourly grid data. Annual averages hide a lot. Hourly intensity for the grids on the carbon table, from a source whose licence allows republishing.
  4. Translations. Arabic, Serbian, Traditional Chinese, Tagalog and Sinhala first, for the readers the carbon table was built for.
  5. Water. Site water use beside any contributed row, as its own field. The index has none, and the two public per-prompt figures are measured on different boundaries and units of work.
  6. Reviews. A second pair of eyes on any figure on the site, starting with the ones that get cited most.
